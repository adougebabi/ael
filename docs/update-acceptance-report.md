## 用户约定

- `ael upgrade`：升级本机受管安装、缓存完整分发、登记本地来源。
- `ael update`：先检查当前目录已有 `.ael/project.yaml`，有则更新该项目。
- `ael update --project PATH`：从任意目录更新明确指定的已接入项目。
- 当前目录未接入时拒绝，不初始化、不转成本机升级、不扫描其他项目。
- `./ael update` 使用项目入口；`./ael upgrade` 不注入项目参数。
- 旧刷新命令不再提供或作为别名接受，返回错误及新入口指引；help、当前 README、Skill 和安装器均改用新命令。历史 0.1.4 报告中的旧命令仅为历史记录。

## 实现

`internal/bootstrap/upgrade.go` 统一本机安装/升级与脚本安装，校验四平台包、notice、版本及本机二进制，拒绝用户二进制改动、降级和同版本不同内容。分发先暂存复核再改名，旧程序和安装元数据备份。`upgrade-intent.json` 保留二进制替换与元数据提交的中断状态；重试只接受对应包。缺失缓存可以补回，真正 no-op 不重写登记信息。

`update_project.go` 在来源和当前程序不同（包括同版本不同构建）时，委派给来源包本身执行；新程序使用自身嵌入的入口/Skill/引用，不能混装旧资源。`update_validation.go` 校验 15 个必要资产，返回与来源包 hash 绑定的完整回执；委派方核验磁盘、锁内容和资产所有权清单，不能仅凭版本或状态通过。

`update_maintenance.go` 将 idle 检查、维护标记、代次及条件触发器置于同一个 SQLite `BEGIN IMMEDIATE`。新版 Claim 在自身事务检查维护/代次，旧内核现有 SQL 也被维护触发器阻挡。它覆盖更新窗口内的写入，不自动停止或热替换已有服务。更新成功后仍需重启旧服务。

预览只用只读 SQLite URI 检查既有运行库，完整检查受管资产冲突，不创建数据库或安装文件。正式项目更新备份旧受管资产，保留 ID、模式、自定义配置字段、业务文件及任务记录。中断后保留屏障与原备份；同源、已停止 owner 才能 `update --ack-stopped` 继续；备份损坏时仍保持屏障。

## 真实旧版到新版演练

实际运行：

```sh
python3 scripts/update_acceptance.py --bundle dist \
  --old-archive dist/ael-0.1.3-unix.tar.gz \
  --out /tmp/ael-update-final
```

使用真实 0.1.3 分发中的二进制、锁和原安装器创建隔离旧安装及旧项目，随后调用真实 0.1.5 二进制。所有运行数据位于测试根之外的独立 runtime，没有业务账号、数据库或生产目标。

14 类检查全部通过，`/tmp/ael-update-final/results.json` 和 `commands.json` 保存输入、命令、stdout/stderr 与结果：

1. 本机预览不改旧安装或项目文件。
2. 本机真实升级并保留旧二进制备份。
3. 本机升级后项目仍锁定 0.1.3。
4. 真实旧版 claim 和工作区 fence 使项目更新拒绝；没有伪造进程停止。
5. 正常恢复该无进程的测试 claim 后，当前目录 `update` 直接更新项目。
6. 项目启动器、四平台运行时、锁、Skill/引用实际变为新版本。
7. 原 project_id、mode、自定义配置字段、AGENTS 用户文字及 app.py 字节不变。
8. 任务定义、检查点和结果文件未被更新操作重写为绿色状态。
9. 项目入口 `update` 与 `--dry-run upgrade` 分别作用到正确范围。
10. 空目录 `update` 拒绝且不生成 `.ael`。
11. 从空目录 `update --project PATH` 使用明确目标。
12. 旧刷新命令拒绝；用户改 Skill 时预览报冲突且不写任何项目文件。
13. 本机与项目重复调用为 no-op；登记内容不漂移。
14. 新安装脚本通过同一 native upgrade 实现实际安装。

另以当前源码构建一个故意使用不同 build ID 的真实可执行文件，验证它委派给目标分发，返回完整 15 项资产回执且实际文件一致，记录 `/tmp/ael-update-final/delegation.json`。这是跨构建协议检查，不宣称某个未发布未来版本已经实测。

已有通用工作流脚本同步去除旧入口和版本硬编码；在 `/tmp/ael-update-workflow-regression` 的 12 项安装 CLI 分支全部复验通过。它仍是明确的确定性协议驱动器，原新 Codex 会话配置阻塞没有因此被宣称解决。前端未改视觉，TypeScript/Vite 构建通过。

## 故障与交付边界

首次原生演练发现布尔参数吞命令，已修正；一次并行构建清空 embed 目录导致 race 编译失败，最终检查改为构建完成后串行执行并通过。独立复核发现缺缓存 no-op、事务竞态、委派混装和损坏备份释放屏障，均已修复并增加对应回归。

当前没有在线发布源，`upgrade` 检查登记的本地分发，`--from` 可明确替换来源；不会假装下载互联网最新版。真实全局 `/Users/vinson/.local/bin/ael` 仍为 `0.1.3 / ada13c4`。要在该机器启用新命令，须先从新分发执行一次 `./dist/ael-darwin-arm64 upgrade`；这次没有擅自执行该正式安装，也没有更新任何未指定的业务项目。

更新后的已有服务需要重启；运行实例依赖原 `AEL_DATA_DIR`，命令不会扫描其他进程环境来猜测。回退须使用报告中的旧资产/安装备份和匹配的运行数据，不靠删 manifest 或改数据库绕过冲突。
