# AEL V2 串行任务总表

“V2”是本轮升级的计划代号，不要求产品直接发布为 2.0.0。

**任何时刻只做一个编号任务。** 该任务的必需验收、回执和检查点全部完成，再进入下一编号。下表是导航，不是让执行者同时展开全部工作包。

| 编号 | 任务 | 本项收口后可以得到什么 |
|---|---|---|
| [V2-00](tasks/V2-00.md) | 基线核对与串行实施账本 | 建立不依赖 AEL 的可恢复开发现场；只核对必要事实，不开启全仓库重构。 |
| [V2-01](tasks/V2-01.md) | CLI 默认可读，JSON 显式选择 | 用户直接执行命令能够读懂状态；已有 Agent 与脚本仍有稳定机器接口。 |
| [V2-02](tasks/V2-02.md) | 父任务与叶子任务：最小可用任务树 | 一个大任务真正拥有可独立执行和验收的子任务，而不是正文里的清单。 |
| [V2-03](tasks/V2-03.md) | 拆分计划：复用用户分项与 Agent 辅助补全 | 把大范围要求变成有边界、有依赖、有验收覆盖的叶子任务，且可幂等应用。 |
| [V2-04](tasks/V2-04.md) | 顺序推进与后继领取 | 一个子任务收敛后，执行者无需等用户说“继续”就能处理下一个已授权任务。 |
| [V2-05](tasks/V2-05.md) | 大任务进度与工作台接通 | 用户打开父任务就能看见具体完成项、剩余项、验证状态和卡点。 |
| [V2-06](tasks/V2-06.md) | 停滞检测、重复失败与可恢复停止 | 把无执行者、健康长任务和真实无效循环区别开，阻止重复消耗。 |

| [V2-11](tasks/V2-11.md) | 跨设备候选、规范快照与执行上下文 | 云端能知道 Agent 实际检查了哪个版本，并让另一设备获取同一份规范依据。 |
| [V2-12](tasks/V2-12.md) | 外部 Agent 主导的远程工程闭环 | 代码仍在执行者机器修改，中心服务真实接收领取、进度、验证与结果。 |
| [V2-13](tasks/V2-13.md) | 双执行者协作、断网与恢复 | 本地开发和云电脑验收能可靠交接，避免双写、丢提交或离线伪成功。 |

| [V2-22](tasks/V2-22.md) | 打包后的全链路验收与交付核对 | 以完整工程行为验收 V2，而不是把单元测试数量作为完成依据。 |

## 阶段检查点

**A · V2-00—01：先建立可恢复的串行开发，并交付 CLI 可读输出。**

**B · V2-02—07：先把大任务本地闭环做可靠。**

**C · V2-08—14：再接中心服务与跨设备执行。**

**D · V2-15—17：把 UI/UX 发现、证据与复验接通。**

**E · V2-18—21：发行升级、部署恢复与旧数据迁移。**

**F · V2-22—23：隔离全链路验收，再做授权的真实双机验证。**

## 顺序不能被“先做基础设施”打乱

先完成本地的大任务分解、逐项验收、连续推进、停滞与集成收口，再服务化。不能先花大量时间搭所有远程抽象，把大任务本身的问题留到最后。

服务化也按可运行行为逐项推进：安全登录 → 两客户端读写同一任务 → 证据跨端可读 → 上下文版本对齐 → 外部 Agent 实际工作 → 双端故障恢复 → 同一看板。

每项任务已有相应 CLI/API 或界面验收，不存在“最后一个任务统一补齐前端和联调”的安排。

V2-23 是唯一计划内的真实外部机器部署与业务切换阶段。缺访问/授权时应明确 BLOCKED，不能把前面完成的软件重新拆开做到处一半。
