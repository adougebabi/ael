# V2-04 · 顺序推进与后继领取

**前置：** V2-03 已 DONE，且其回执存在。
**执行纪律：** 先读 `../00-EXECUTION-CONTRACT.md` 与 `../WORKLOG.md`，只实现本项；本项 DONE 后才读取下一任务正文。
**目标：** 一个子任务收敛后，执行者无需等用户说“继续”就能处理下一个已授权任务。

## 实施内容

1. 实现父范围内的 next-work 查询与领取，原子检查依赖、能力、授权和 WIP；稳定顺序，不能随机领取容易的项逃避当前失败。
2. 默认单 Runner 只持有一个开发叶子任务，完成必要验证后再领下一项。产品可显式允许多个 Runner 处理无冲突子任务，但不得把同一执行单元发给两人。
3. Attached Skill 按 next_action 继续；Managed 父运行器协调，子执行器只返回当前结果，禁止递归启动完整 loop。已有只运行单 task 的入口兼容。
4. 将等待人、等待能力、依赖未满足、Runner 离线、预算停止明确区分；所有有界循环退出必须有 checkpoint 和 stop_reason。不能把 max_steps 达到当成正常完成，也不直接设成无限循环。
5. 主子任务状态分别记录；一个角色提交后不负责安排下一个 Bot，后继领取机制负责承接。

## 必须通过的本项验收

- [ ] 1 父 + 3 个有依赖的叶子任务，执行器连续完成前两项并取得第三项，不需用户消息。
- [ ] 第二项第一次验证失败，仍在第二项修复；不开始第三项，成功后再前进。
- [ ] 没有具备下一能力的 Runner 时显示等待，不做无意义空转。
- [ ] 进程重启恢复到未完成单元；重复 submit 不重复创建/领取。
- [ ] 单任务旧路径仍通过原有回归。

## 边界

先用本地模式跑通；不通过新增总控 LLM 每一步重新规划来实现顺序推进。

## 结束动作

完成所有必需验收 → 生成 `../receipts/V2-04.md` → 保存本地 Git/补丁检查点 → 更新 WORKLOG 为 DONE → 运行账本检查器。
无需再次请求“继续”；在既有授权范围内直接进入 V2-05。存在真实阻塞则只保留本项 BLOCKED，不开后续任务。
