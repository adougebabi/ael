# 本地非阻断问题记录

本文件只记录实施中发现、尚未纳入当前任务的非阻断问题；实施进度仍以 `WORKLOG.md` 为准。

## NB-001 · 现有 outbox 的外部编辑竞争窗口

- 位置：`internal/store/store.go` 的 `flushOne` 与 `Atomic`（当前约第 173、221 行）。
- 现象：只读复核发现，outbox 在读取并校验目标内容后，创建临时文件并最终以重命名替换；若不受 SQLite 锁约束的外部编辑器恰在校验和替换之间修改或创建目标，现有机制可能覆盖该次编辑。
- 证据状态：基于现有代码路径的静态发现，尚未在隔离夹具中重现精确竞争时序；不把它报告成已修复或已发生的数据丢失。V2-03 的计划应用会在登记写入意图时核对期望版本，outbox 也会拒绝其检查时已存在的冲突，但这不消除上述窗口。
- 后续建议：在明确授权的独立工作中，以临时文件和可控同步点复现；设计并验证不覆盖外部写入者的跨平台替换与恢复语义，再评估对既有 outbox、升级和恢复的影响。
- 本轮处理：按用户要求先记录，不扩展修改现有通用 outbox 替换机制。

## NB-003 · Runner checkpoint 的跨工作区备份语义待后续定义

- 现象：当前 V2-04 验收范围是同一运行库的进程重启恢复。完整备份恢复到另一运行库时，既有恢复路径不会复制新的 Runner assignment/checkpoint；旧租约也不应自动复活。
- 证据状态：依据本轮代码路径静态核对；尚未将跨工作区恢复作为 V2-04 的通过项，也未声称可以自动续跑。

- 本轮处理：按用户要求记录，不扩展本项到跨工作区备份或远程 Runner。

## NB-004 · linked worktree 的 `.git` 文件进入现有候选指纹

- 位置：`internal/core/candidate.go` 的 `Fingerprint`。
- 现象：只读核对发现，该函数跳过目录形式的 `.git`，但 Git linked worktree 的 `.git` 通常是包含本机 `gitdir` 路径的普通文件，当前会被计入工作区内容指纹；即使源码与提交相同，不同 worktree 可能因此得到不同指纹。
- 证据状态：基于代码路径和 Git linked worktree 的文件形式作静态判断，尚未在隔离夹具中实测；不声称已修复或已造成数据错误。
- 本轮处理：按用户要求先记录，不顺手调整现有通用指纹；本项集成验证须明确其候选和纳入依据，不能把该指纹误作跨工作区相等的证明。

## NB-005 · 修改无进展提示间隔可能改变候选指纹

- 位置：`internal/core/policy.go` 的 `policyHash` 与 `internal/core/candidate.go` 的 `Fingerprint`。
- 现象：只读核对发现，V2-06 的政策哈希刻意排除 `no_progress_seconds`，但现有候选指纹仍纳入整个规范化的 `.ael/policy.yaml`。若任务已有候选后修改这一提示间隔，候选指纹可能变化并要求重新执行，和 `docs/stagnation.md` 中“不改变候选”的说明不一致。
- 证据状态：基于两处代码路径静态判断，尚未在隔离夹具中实测；V2-06 的验收夹具均在创建任务前设置该间隔。
- 本轮处理：当前集成验收可使用稳定政策，不受此问题阻断；按用户要求只记录，不在 V2-07 顺手调整旧指纹或文档。

## NB-006 · 一次性人工或模型结论在领取前的观察时段缺少持续证明

- 位置：`internal/core/verify.go` 的 `review` 与 `internal/core/assessment.go` 的一次性 `Assess`。
- 现象：两条既有入口先接收观察结果及读取引用，随后才创建检查 attempt。只读复核推测，若观察发生在领取之前，而其他写者曾临时改变候选并在领取前还原，仅凭提交时的相同指纹不能证明观察期间候选始终不变。
- 证据状态：静态时序分析，尚未独立实测；不声称已发生错误结论。已经预先领取的父级检查采用本项的重叠工作标记；这一记录针对领取之前、旧入口原本就无法覆盖的观察时段。
- 本轮处理：按用户要求记录，不在 V2-07 顺手重做既有人工或模型审核交互；后续需要时应在实际审阅开始时绑定可核验的候选和观察会话，并验证并发写入、重试与人工结论的版本保护。
