# AEL V2：逐项闭环实施契约

> 本文用于整改现有 AEL 仓库，不是安装到业务项目的 AEL Skill。
> 本轮由本地 Codex 或其他 Coding Agent 直接开发 AEL；**不得用 AEL 管理这次 AEL 开发任务**。
> 所有新命令名称为设计建议；实现时统一最终接口，并同步帮助、Skill、测试和文档，不能让示例与实际命令脱节。

## 当前裁定 AD-AGENT-DRIVEN-01

当前产品边界以 `../v2-agent-driven-revision/00-ARCHITECTURE-DECISION.md` 和修订任务正文为准。修订包中“V2-12 当前、后续只改说明”的文字属于当轮恢复快照，后续进度与用户授权以 WORKLOG 为准。Agent → Client → Server；不启动 Agent、不强制客户端 Docker、不复制/回写源码、不监督进程或掌管模型/发布凭据。原可信 Runner/本地 Docker 必需补充中的冲突条款停止生效；原文保存在 history/pre-AD-AGENT-DRIVEN-01 及 Git。稳定 Local Managed 显式功能保留兼容，不是远程前置。

## 1. 本轮交付目标

在现有 Go / Vue / SQLite 基础上实现：

1. 大任务可以复用用户已经给出的拆分，也可以由 Agent 辅助拆分；每个叶子任务完成自己的实施与验证，父任务汇总并做集成验收。
2. 连续执行能从已完成子任务转到下一个可执行子任务；发现停滞、重复失败或缺少执行者时给出具体原因，不靠用户反复说“继续”。
3. 支持一个可选的中心服务。Mac 与云电脑通过 API 共享任务、执行、证据和同一个 Dashboard；代码仍在各自 Git 工作区，实际工作由本地执行者完成。
4. UI/UX 验收提供结构化问题、真实图片/交互证据、人工裁定、关联修复与复验。
5. CLI 默认人类可读，机器使用显式 `--json`；服务端、CLI、项目入口各有清楚且方便的升级路径。
6. 保留现有本地模式、有效的并发/版本/证据保护和已实现的界面，不重写一套框架，不顺手重做视觉。

本轮不是：新的多 Agent SDK、通用工作流编辑器、自动产品规划平台、多主离线数据库、跨云部署平台或容器编排系统。

## 2. 最重要的约束：当前开发一次只做一个任务

### 2.1 不自托管

- AEL 仓库根目录不得为本次开发执行 `ael init`，不得安装/启用工作入口、创建 `.ael/work-items` 或调用 AEL 的 `claim/submit/loop` 来管理本任务包。
- `assets/skills/ael-work/` 是**产品代码和测试对象**，不是本仓库的活动工作指令。可以修改和测试，不能因此接管当前开发会话。
- 可以在明确的临时 fixture、独立测试仓库和容器中启动 AEL、创建任务并测试 Loop。测试完成清理自身进程，不影响真实业务项目。
- 当前开发仅使用本任务包、普通 Markdown 工作账本、Git 和常规测试工具。不要为实施账本再写一个调度框架。
- 若本地存在用户自定义 AGENTS 等指令，先识别冲突并遵守宿主权限；不删除、覆盖或偷偷绕过。可继续做不冲突的只读核查。

### 2.2 全局 WIP = 1

实施顺序固定为 V2-00 → V2-23。状态仅为 `PENDING / ACTIVE / VERIFYING / DONE / BLOCKED`。

- 任意时刻，`ACTIVE + VERIFYING + BLOCKED` 的任务合计不得超过一个。
- 开始 V2-N 前，所有更早任务必须 `DONE`。未来任务保持 `PENDING`，不提前创建它们的业务骨架。
- 一个任务的顺序是：**理解本项 → 补失败用例/验收入口 → 最小实现 → 实际验证 → 修复本项缺陷 → 保存回执 → 本地检查点 → DONE → 下一项**。
- 不能“先把所有后端写了再补前端”，不能“先给全部任务建接口最后联调”，不能“本项差一点，先做下一项”。
- 当前任务涉及的必要共享代码可以修改；未到期功能的实现不能借“顺手”“以后会用”提前铺开。
- 可用审查/测试子 Agent，但它们只围绕**同一个当前任务**，默认只读或在隔离目录运行测试。不得让多个 Agent 各做不同编号任务，也不得多个写入者同时改同一工作树。
- 产品本身最终允许多执行者并行；这不改变**本次框架开发**全局 WIP=1 的规则。

### 2.3 自动继续，而不是每项请求批准

普通任务验收通过后，更新账本和回执，直接继续下一编号，不反复询问“要不要继续”。V2-12 已按当轮要求完成并暂停。用户已进一步授权“继续，直到所有都完成”，按 WORKLOG 从当前项逐项推进到 V2-23。真实外部条件和具体部署授权仍按对应任务核对。

遇到下列情况才停：真实权限缺口、无法获得的外部条件、关键需求矛盾、无法安全恢复的数据问题、当前会话已无法继续。必须记录精确阻塞和恢复动作，不虚构后台执行。

阻塞时不擅自跳过当前任务；不要为了制造进度另开五个任务。只要不是外部阻塞，应在当前任务内部继续定位、修复和验证。

## 3. 防止另一种长时间空转

### 3.1 本次开发的复核规则

- 每完成一个可运行的行为，或取得一个失败结论，更新当前任务的简短进展；不按每条命令记流水账。
- 每经过约 45 分钟实际工作进行一次自查：当前验收项是哪一条？增加了什么可复核结果？是否扩大了范围？这只是检查点，不是自动判失败或时间承诺。
- 同一个验收失败连续出现 3 次且没有新证据时，停止重复修改，先做一次限定范围的根因复核；保留失败输入、最近差异、已排除原因和下一条验证假设。
- 根因复核仍无进展时，将当前任务标为 `BLOCKED`，提交可恢复现场。不得无限重试、重建任务、改标题或重置计数规避限制。
- 长时间测试/构建不是默认空转：保留进程、阶段、运行日志和配置的超时；不以“没有代码提交”认定失败。
- 不能通过删失败测试、放宽断言、把必需检查改可选、全部 skip 来获得 DONE。

### 3.2 当前任务过大时

允许把**当前任务内部**划成至多几个有顺序的验证小步，写在本项回执中，仍然只有一个 ACTIVE。当前任务全部完成前不得进入下一编号。

若发现计划的前置遗漏，只能：
1. 必要且小的前置作为当前任务的一部分实现并说明；或
2. 明确写出计划修订和依赖理由，先完成这个前置。

不得通过反复“重排规划”替代开发，也不得把当前未实现的验收项移到未来从而宣告完成。

## 4. 账本、证据与会话恢复

### 4.1 只维护一份进度权威

任务包中的 `WORKLOG.md` 是本轮实施进度的唯一权威，不用 AEL 保存它。任务说明是验收基线，不把同一状态重复写入多个 JSON/数据库。

每次开工：
1. 读取本契约、`WORKLOG.md`、当前任务文件；无需反复加载全部任务正文。
2. 核对 Git 状态、当前代码与上次回执，识别用户新增修改。
3. 运行 `tools/check_worklog.py` 检查任务顺序与 WIP。
4. 从当前任务未完成的验收项继续，不从 V2-00 重做，不启动后续任务。

恢复只能依据真实文件、测试和产物；不能仅依据上一会话的“我已经完成”。

### 4.2 每个 DONE 必须有独立回执

保存 `receipts/V2-XX.md`，内容保持短但完整：

- 本项目标与实现范围；代码落点。
- 开始基线、最终本地提交或补丁摘要。
- 每条验收：命令/步骤、结果、日志或截图的实际位置。
- 本项的失败修复记录及仍存在的限制。
- 是否涉及数据迁移、是否可恢复。
- `结论: PASS` 与下一任务 ID。

原始大日志和截图可保存在仓库外，由回执引用真实路径；共享时附可移植清单。不得只写“所有测试通过”而不给可复现的命令和目标版本。

附带账本检查器只检查**顺序与回执存在性**，不证明代码正确，也不能代替实际测试。

### 4.3 本地 Git 检查点

在不混入用户未提交改动、且本地策略允许的情况下，每项 DONE 创建一个独立本地提交，建议 `feat(v2-XX): ...` / `fix(v2-XX): ...`。不推送、不发布、不 squash 用户历史，不执行破坏性 reset。

无法安全提交时保存明确文件清单和补丁摘要，在回执说明；不能把用户已有修改一起提交。若后续修改使已完成能力回归，立即在当前任务修复并复跑受影响验收，追加原回执修订，不悄悄改历史 PASS。

## 5. 一项任务的完成定义

除 V2-00 为准备任务外，每项 DONE 要同时满足：

1. 描述的行为真实可用，不是 schema、TODO、占位接口或静态假数据。
2. 本项必要的存储、领域、API/CLI、界面全部接通；仅涉及 CLI 的任务无需人为增加界面。
3. 本项列出的正向、失败、恢复用例通过；相关旧能力未新增回归。
4. 涉及 UI 的任务实际执行浏览器交互；涉及打包的任务测试打包后的程序，不能只测试开发服务器。
5. 新行为的最终命令/接口、Skill 和帮助一致；不存在让 Agent 猜测的命令。
6. 回执、工作账本、Git/补丁检查点齐全。

不接受“90%完成”“等其他任务再接线”“功能写了但没测”的 DONE。环境缺失导致**本项必需验收**无法完成时标 BLOCKED；可选的跨平台实机验证单独标注，不能伪装成测试通过。

## 6. 技术边界：复用现有核心

### 6.1 任务层级与进展

- 只增加父任务 Epic / 叶子 Task；Attempt 仍是执行记录，不是第三层需求。里程碑可作分组，不建立另一套生命周期。
- 叶子任务遵守需求/定义 → 实施 → 验证 → 完成归档；归档保存产物、依据与结果，不另加一道默认人工批准。子任务完成不跳过父级集成收口。
- 父任务保存整体范围、拆分计划、验收映射、集成目标；真正修改发生在叶子任务。父级可以执行规划/集成检查，但不能与子任务同时写同一份业务代码。
- `Parent` 仅表示组织关系，依赖明确声明且无环；取消子任务不能自动满足必需范围。
- 父验收项必须映射到子任务产物/检查或父级集成检查，允许一对多。未覆盖、重复和跨模块遗漏要可见。
- 已验收、已集成、已发布分开；父任务只有必要子任务达标、最终集成候选满足整体验收和交付条件后完成。
- 展示数量、阶段分布、未满足条件、最近成果和具体卡点，不以 tokens/心跳/日志行数/耗时推算完成百分比。
- 用户已有拆分优先复用；Agent 提供结构化拆分建议，不自动重复造任务；明确授权范围内无需每个子任务再次人工批准。

### 6.2 两种部署，一套领域规则

- Local 模式继续可用；Remote 模式由一个 AEL Server 作为任务定义、调度、审批、发现与证据元数据的唯一权威。
- 代码、现行规范、工程政策仍由对应 Git 版本的项目文件维护；服务端保存来源及不可变快照，不产生一份可任意编辑的“第二套当前规范”。
- 远程客户端不能再次导入 Git records/outcomes 覆盖服务端运行态。断网不自动切回本地模式创建第二个权威。
- 执行在 Mac/云电脑已有的外部 Agent 宿主；Client 仅通信，Server 不执行任务 shell，不访问客户端绝对路径，不保存模型/发布凭据。
- 保留共享领域服务；网络层只是传输与授权。不要让 CLI、本地 HTTP、远程 HTTP 各有一份推进逻辑。
- 首版中心服务为单实例 Go + 嵌入前端 + 本机 SQLite + 附件目录。不给客户端共享 SQLite 文件；不要求 PostgreSQL/Redis/MQ/S3。
- project / checkout / workspace / runner / attempt 身份分开。显式注册仓库，不仅凭相同目录名或 remote URL 自动合并项目。
- 候选以 repository + commit + 必要内容清单/哈希及构建标识定位；分支名、时间戳、客户端绝对路径不足以证明相同版本。
- 默认使用稳定、隔离的执行/检查工作区；共享环境写入要单独声明资源约束。未知跨分支影响不复用验收结果。

### 6.3 远程一致性与安全

- 在开放远程变更能力前完成身份认证与项目级授权；现有防跨站 session token 不能当远程身份认证。
- 所有变更使用服务端权限校验、expected revision / fencing 与幂等键；服务端从身份得到 actor，不信任随意填写的 executor 名称。
- 网络不提供“恰好执行一次”的保证。超时先查询既有 operation/receipt，重复提交同一结果幂等；发布等副作用不能盲目重做。
- Runner 主动拉取任务，无需服务器反向连入个人电脑。令牌区分开发、验收、人类批准和管理权限，不给扫描 Bot 默认修改门禁/自动发布权限。
- 租约与心跳记录协作责任与最近上报，不证明宿主进程活性或工作成果；失联不等于旧写进程已停止。隔离工作区仍需拒绝过期提交。
- 远程断网后只允许在既有租约/权限内安全完成当前可本地执行的部分；失去责任后 Server 拒绝新有效提交；Agent 应停止该任务，AEL 不保证宿主 OS 停写或拦截发布，不宣告最终完成。保存待上传产物，重连核对状态后提交。
- 上传内容不执行；文件安全校验、项目隔离、容量限制、授权下载、日志脱敏必须有测试。凭据不进 Git、不出现在 URL/日志中。

### 6.4 验收与更新

- UI/UX 发现是待核实的问题，不是自动成为缺陷或自动否决。模型建议、人工裁定、修复与复验分别记录。
- 人工 pass/fail/blocked 绑定操作者实际审阅的候选/定义/计划；必需门禁不能因“忽略问题”消失。
- 当前仓库已存在的人工结论、幂等和版本校验优先复用，不退化成仅 pass，也不重复建设。
- 发布构建与正式发布分开；生成 GitHub Actions/发布脚本不等于已存在在线 Release。真实 push/tag/Release/Oracle 部署均须明确授权。
- 升级分服务、CLI、协议/Skill；兼容升级不强迫逐项目重装。保留现有离线安装能力与用户自定义资产保护。

## 7. 测试与权限边界

- 本轮测试创建独立 fixture 工程；AEL 仓库是被开发对象，不是 AEL 接管的业务项目。
- 双客户端/双 Runner 的本机容器验证是真实网络与并发测试，但不得称为“已在 Mac + 云电脑 + Oracle 三机验证”。
- deterministic/fake executor 可以测试调度与状态机，必须标明；不能用它声称真实 Codex 已连续完成工程工作。
- 真正外部机器、生产部署和既有资料切换放在 V2-23。此前完成本地代码、发布包、迁移演练和可复核网络验收。
- 不搜索整个 HOME 找业务目录，不读取真实密钥，不修改摇光或其他项目、不自动杀已有 Bot、不覆盖真实数据库。
- 未提供实际“大任务”原始资料时，只做合成夹具。不能从任务名称推断其全部要求，更不能伪造用户实际任务的完成比例。

## 8. 给用户的阶段报告格式

每完成一项，报告一小段：

```text
已完成：V2-XX / 名称
交付：现在能实际做到什么
验证：实际命令/场景与关键结果
证据：回执路径 + 提交/补丁标识
下一项：V2-YY（已开始） / 阻塞：具体条件
```

不让用户等待十几个小时才知道“全都做了一点”。会话被迫结束时给出 DONE 清单、唯一未完成任务、失败现场、恢复命令；不把后续工作说成已经在后台进行。
