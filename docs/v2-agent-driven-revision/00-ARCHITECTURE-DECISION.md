# 架构裁定：AEL 管工程协作，Agent 管实际执行

修订标识：`AD-AGENT-DRIVEN-01`。本次用户已经明确了产品边界；不再比较原生沙箱、Docker 任务后端、APFS 等候选路线。

## 1. 目标架构

- Oracle：Docker 部署 AEL Server + Dashboard，持久化任务、规范快照、状态、发现、回执和证据。
- Mac / 云电脑：现有 Codex、Bot 或其他 Agent 按 AEL 工作 Skill / 协议处理工作，通过 AEL CLI / 脚本调用 HTTPS API。
- 编码、构建、测试、浏览器、截图、Git、CI 和生产部署由 Agent 的宿主及项目现有工具链执行。
- 本地使用 Docker、虚拟机、worktree 或普通目录由项目和宿主决定。AEL 可以给建议，也可以记录实际环境，但**不把本地 Docker 作为领取或提交的通用前置**。

调用方向是 **Agent → AEL Client → Server**，不是 **AEL → Agent → 项目命令**。

这里的 Client 可以保留已有 `runner` 的协议标识以兼容数据；不为换名字做全仓库迁移。UI/文档优先称“执行者接入”或“Agent 客户端”。

## 2. 三方职责

| 部分 | 应负责 | 不应负责 |
|---|---|---|
| AEL Server | 任务与拆分计划、可领取单元、规范引用、授权、责任版本、进度、证据接收、门禁判定、下一动作、统一看板 | 启动 Codex、执行项目 shell、SSH 到客户端、给宿主杀进程、管理容器或本机凭据隔离 |
| AEL CLI / 通信脚本 | 接入/鉴权、领取/续租/交接、取上下文、明确范围的本地资料采集与上传、幂等提交、回执查询、可读输出 | 生成任意 shell 后执行、接管模型会话、编排项目进程树、自动复制/回写工作区、推送/合并/发布 |
| Agent + 工作 Skill + 现有宿主 | 读规范、理解/拆分任务、执行本项工作、调用已有工具做检查、提交真实结论、消费 next_action、遵守授权和失败预算 | 随意改服务端任务状态、伪造证据、用旧版本结果满足新门禁、绕过项目权限 |

CLI 可在用户明确选择的项目和文件范围内读取文件、计算哈希、查询 Git 元信息，或持久化上传重试状态。它不运行用户提交的构建/测试脚本。凭据不进入任务上下文、展示输出或 Git。

## 3. AEL 不执行检查，但仍判定工程结果是否达标

必须保留三个不同事实：

1. **执行**：Agent/CI/人工实际运行了检查或审阅。
2. **报告**：提交者报告检查对象、方法、观察、结果、相关日志和截图。
3. **判定**：AEL 校验来源权限、任务/验收/计划版本、候选关系、产物完整性、必要检查覆盖，再按现行规则决定是否推进。

AEL 可以要求某项验收条件必须有证据，也可以引用项目原本批准的命令或独立验收要求；它不因此变成编译器、浏览器或命令沙箱。

文件哈希证明接收内容与声明一致，不证明测试确实运行或结论真实。记录必须区分：外部命令报告、Agent 语义判断、场景验收、人工结论、可核验 CI 回执。普通执行者不能自报成另一个验收人；需要独立验收的任务仍由相应身份提交。

不允许客户端直接 `status=done`。报告不足、缺少必要检查、候选不符、授权不足或明确失败，仍不能通过门禁。只验收报告交付与产品验收通过继续分离。

## 4. Loop 如何继续

一次活跃 Agent 会话遵循：

领取当前责任 → 读取规范和验收条件 → 用宿主工具做工作 → 上传实际进度和证据 → 提交结果 → 读取并消费下一动作。

| Server 返回 | Agent 的责任 |
|---|---|
| 当前责任可继续 | 在当前授权内继续，不再询问一次“是否继续” |
| 实现失败需修复 | 留在同一叶子任务修复，保留失败证据，不跳到下一依赖任务 |
| 需要重新分析 | 处理确实受影响的方案/范围；关键变化走既有授权 |
| 当前叶子已达标，存在后继 | 能力和授权满足时申请下一项；先通过领取，不凭 next 查询直接工作 |
| 交接 | 当前角色结束，将下一单元留为可领取；已有外部 Bot 自行轮询/订阅后领取 |
| 等人工/环境/能力 | 保存现场，给出准确恢复条件，不循环伪进展 |
| 任务完成/取消 | 停止当前工程工作；完成后反馈走关联新工作项 |

AEL 提供 next-work / next_action / 原子 claim，不负责制造新的活跃 Agent。用户现有 Bot 框架或会话运行机制负责唤起执行者。所有 Agent 退出后，看板显示无人接手；不能承诺无人运行时仍会自动编码。

Skill 是这条协议的具体用法，不是一个能自动保活会话的后台进程。必要的短期续租/上传助手可以只做通信，不能重新发展成进程托管器。

## 5. 并发、租约和停止的真实含义

- 责任租约/fence 保护的是 AEL 接口接受当前协作结果的权利，不是宿主 OS 的文件写权限。
- Server 撤销责任或更新版本后，相关新结果、有效证据关联和推进请求必须拒绝过期身份。
- CLI 获知撤权或期限到达，停止把该 Attempt 当作有效写入来源，保留草稿；旧回执查询是只读，不等于新授权。
- 工作 Skill 要求 Agent 停止该任务并处理交接；AEL **不保证**宿主终止了进程、不杀任意后代、不撤销文件描述符。
- 协作心跳/Agent 自报阶段不证明编译器或浏览器仍在运行。没有本机观察依据时状态为“最后上报”“已失联”“执行状态未知”。
- “暂停任务”表示暂停 AEL 协作推进；“请求停止工作”是给执行者的请求，不展示“已终止进程”。
- 失联不能作为同一可写工作区安全复用的证明。重新领取保留旧责任历史；同一工作区未知状态按政策要求人工确认或明确换用独立工作区。AEL 只记录和校验声明，宿主负责实际工作区隔离。
- 断网不自动切本地新权威。过期结果不得自动套用新 Attempt；只允许经显式恢复与版本核对后重新提交或归档为诊断。

## 6. 候选、成果和发布

- 代码留在 Agent 自己选择的工作区；AEL 不再默认新建副本并在提交后回写原 checkout。
- 在验证前确定候选；报告关联受检输入、必要环境和版本。开发后的新候选与之前的测试输入不相同，必须重新验证或证明允许的复用。
- Server 对上传字节、元数据和关联做校验，不能访问客户端绝对路径或核验其未上传的全部本机状态。
- 已接收证据是固定内容；后续改本地同名文件不能改变服务端原件。
- 合并/发布由外部 Git、CI、部署工具和用户权限处理。AEL 保存相关授权、目标、回执及验证，不自行调用 `git push`、部署命令或自动回写。
- `verified`、`merged`、`released` 目标继续不同。明确要求合并/发布的任务必须有符合该目标的结果，不能因 AEL 不执行部署就降为仅报告完成。
- AEL Token 不自动获得 Git/云平台权限；AEL 无权承诺能拦截宿主已经拥有权限的任意外部命令。实际发布控制属于外部凭据/环境和用户审批策略。

## 7. 仍然必须保留的安全要求

Server 身份与项目授权、有效责任校验、版本冲突、幂等、文件安全与配额、授权下载、基本凭据脱敏、不可篡改的历史引用均不削弱。

Agent 有意调用 CLI 使用本身份能力，不存在“必须证明 Agent 绝对读不到自己的 AEL 使用凭据”的产品承诺。仍应最小权限、撤销可用、凭据不落 Git、不出现在可读输出/日志/上传上下文里。同一 OS 用户下的强对抗隔离不由 AEL 承诺。

禁止将范围修订做成 `--ignore-security`、恒真开关或测试 overlay。允许受支持的薄客户端通信，但旧的未验证远程进程托管入口不得因此恢复启动能力。

## 8. 现有本地执行能力如何处理

已稳定存在的 Local Managed/命令便捷入口，本轮不为了纯粹的架构一致性推倒删除；按历史显式功能保持旧回归、标注边界，不接入远程默认链路，也不成为 V2 新能力前置。

V2-12 新增但尚未通过的远程进程托管、APFS/容器隔离、自动复制/回写、进程树看护应退出活动路径。保存代码检查点和失败证据；不继续加固这些路线，不另做一个可选远程执行平台。

不能让通信客户端与旧托管入口共享一个“未验证宿主隔离所以全部 503”的总门禁。新通信路径保留真实权限和版本门禁；旧托管功能明确不支持或不暴露。

## 9. 本轮实施纪律

AEL 不自托管。原 WORKLOG 是唯一实施进度权威。V2-00—11 保留已有状态与历史回执；V2-12 内只处理本次边界直接影响的前置行为，追加回归结果，不重开全部任务。

后续 V2-13—23 只修订说明和验收假设，不提前实施其功能。V2-12 是当前唯一进行项，按修订验收通过后暂停，未经继续指令不启动 V2-13。

本裁定替代旧“可信 Runner 有限收口”和强制本地 Docker 路线中冲突的执行要求，不追认历史失败为已修复，不宣布当前代码已通过。
